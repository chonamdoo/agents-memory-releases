# 정식 v1.0.0 출시 계약

2026-11-03(KST). 이 문서·[후보 명세](candidate.json)·[점수표](SCORECARD.ko.md)를 정식 출시의
단일 관리 기준으로 사용한다. **v1.0.0은 목표 버전이며 아직 출시된 버전이 아니다.** 현재 권장
후보 c3의 source package 버전은 1.0.0이지만 미출시 빌드 준비다. 정식 배포물·Mac/프로필 품질
확인 전에는 tag/release/asset을 게시하지 않는다.

## 선택한 후보와 지원 범위

- 후보 `hindsight-local-v1.0.0-c3`: `agents-memory@30706fc1c1e6a7d5aaccee3bf643b0370bbaf5be`.
  Hindsight `14e7306e27cdbd03ad5f17cf46f22a5f6d6ec5a2`와 검토된 내부 admission patch를 사용한다.
- macOS Apple Silicon, 로컬 **단일 사용자** 설치. 회사용이라는 이름은 팀·다중 사용자 ACL
  지원을 의미하지 않는다. 개인은 **Jev**, 회사는 설치 시 선택한 **구독 CLI 하나**다. 실제 host와
  정확한 모델·설정은 검증 증거에 기록한다. 미검증 host까지 지원 완료로 일반화하지 않는다.
- Hindsight 내부에서 동일한 저장 판단 계약을 실행한다. None/chunks, E5-small ONNX, RRF,
  observations/reflect 비활성 구성을 유지한다. 별도 검색 LLM·Neo4j·새 저장 계층은 추가하지 않는다.
- 사용자 입력은 로컬 outbox에 접수하고 독립 작업자가 전송한다. 접수와 검색 가능 상태를
  구분하며 ACK 유실에 따른 중복 가능성을 유지한다. exactly-once·공개 SOTA는 출시 보증이 아니다.
- 기존 Native preview와 자동 설치 대상을 임의로 바꾸지 않는다. 소스·런타임·모델·DB 전제,
  라이선스와 설치 방식이 검증된 **새 배포물**을 만들며 옛 binary의 이름만 바꾸지 않는다.

## 100점의 뜻

**검증 완료 점수**이지 정답률·안전 확률·SOTA 점수가 아니다. 행마다 수용 조건을 모두 만족해야
해당 배점을 얻는다. 개인·회사 모두 통과해야 공통 점수에 반영한다. 미검증은 보류(0점),
실패는 미달(0점)이며 서로 다른 상태로 기록한다. 모든 행이 필수이므로 **100/100일 때만 정식
배포**한다. QA 90%를 충족해도 다른 항목을 생략할 수 없다.

## 현재 점수와 증거 갱신

현재 공동 출시 점수는 **15/100, 정식 배포 차단**이다. 개인은 **50/100**, 회사는 **15/100**이다.
[C54 실제 클라우드 역할 대체 시험](VERIFICATION-C54-CLOUD-SURROGATE.ko.md)에서 현재 c3의
실제 Jev 저장 판단·통합·안전 항목을 확인했다. [C3 검증](VERIFICATION-C53-20261103.ko.md)의
회귀 421개와 함께 이번 소스에 결합한 새 실행 receipt만 인정한다.
회사 Mac + Codex는 대상 설정이며 실제 연결·설치 검증을 이관했다는 이유로 점수를 주지 않는다.

[C51 실제 검증](VERIFICATION-20261103.ko.md)의 c1 당시 개인 50점은 보존한다. C52에서
지원되는 Hindsight 키의 로컬 capture 반례를 확인해 안전 15점 인정을 철회했고, 당시 점수는
개인 35 / 회사 15 / 공동 15였다. 원래 통과한 20개 backend 시험은 실패로 다시 쓰지 않는다.
[철회 기록](evidence/security-withdrawal-c52.json)·원래 receipt·[이전 후보 명세](history/c1-candidate-superseded-20261103.json)를 보존한다.
c3는 해당 키 형식을 고쳤지만 소스가 바뀌었으므로 과거 실제 프로바이더 receipt를 자동 이전하지
않는다. C53 당시 새 후보의 15점과 C54의 개인 50점은 QA 정확도가 아니라 해당 소스에서 실제로 확인한
검증 범위를 뜻한다. 공동 15점은 회사 프로필의 실제 확인을 생략하지 않은 결과다.

```sh
python3 tools/stable_release_gate.py render > release-candidates/v1.0.0/SCORECARD.ko.md
python3 tools/stable_release_gate.py check
```

`check`는 통과 시 0, 미검증/미달 시 3, 잘못된 명세 시 2로 종료한다. 증거는 후보 디렉터리
안의 JSON과 SHA256으로 연결한다. source commit·digest·upstream·patch·목표 버전·platform이
바뀌면 이전 증거를 자동 인정하지 않는다. null은 미검증이다. 두 프로필·누락·위조된 bool·
불가능한 분모·해시 불일치·경로 이탈은 통과로 처리하지 않는다.

각 프로필의 host·답변 모델·저장 판단 모델·judge와 runtime 설정도 고정한다. 회사도 사용자가 확인한 Mac + Codex를 대상으로 한다. 구독 저장 판단·답변·judge는 Sol을
대상 설정으로 고정했다. 실제 회사 CLI 연결·Mac 실행 검증은 사용자 지시에 따라 이관했고,
해당 점수를 부여하지 않았다. 개인의 Codex/Sol도 사전에 고른 대상 설정이다. 값이 채워졌다는 사실이 실제 caller/Mac 실행
성공을 뜻하지 않는다. 실제 Jev 시험은 저장 판단과 backend 수명주기/경계 행에만 반영한다.
증거의 canonical 설정 해시와 역할별 모델·host가 일치해야 한다. QA 대조군에도 동일 workload,
공식 upstream, 고정 설정, 100개 완료·누락/오류 0, 첫 답변 lock을 요구한다. 파일은 **한 번 읽은
같은 바이트**로 해시와 JSON을 검증하며 측정 횟수·호출 수에는 정수만 허용한다.

검사기는 **저장된 실행 증거의 일관성을 검사**한다. JSON의 `actual_provider=true`나 해시가
실제 실행·계정·모델의 진위를 독립 증명하지 않는다. 운영자는 원래 실행 receipt·trace·기기·
최종 artifact와 독립 검토를 확인한 뒤 정제된 집계를 기록해야 한다. 원문 정책·질문·정답·
비밀값·계정 로그는 공개 저장소에 올리지 않는다. 현재 core receipt도 private 실행의 정제된
집계이며 실제 모델 QA가 아니다.

## 유한한 종료와 배포

1. 이 기준을 결과에 맞춰 완화하지 않는다. 새 개선 후보 최대 3개, 최종 독립 확인 1회,
   연속 2개가 개선을 못 보이면 튜닝을 중단한다. 초기 source를 기준 후보 c1로 두었으며
   후속 변경과 사용한 실험 횟수를 아래 기록에 추가한다. 판본 변경으로 횟수를 초기화하지 않는다.
2. 전부 통과하면 정식 출시 후보를 고정하고 최적화를 종료한다. 미달 시 원인이 있는 부분만
   수정한다. 후보를 소진하면 자체 계층을 줄이거나 범위를 재설계한다. 보존·보안 문제가
   남아 있으면 배포를 보류한다. 이를 SOTA 연구로 치환해 개발을 계속하지 않는다.
3. 클라우드에서 못 하는 Mac/구독 계정 검증은 해당 항목만 이관한다. 이 이유로 관련 없는
   클라우드 튜닝을 반복하지 않는다. 미검증 상태에서 정식 버전을 발행하지 않는다.
4. 배포 직전 현재 표를 다시 생성해 `check` exit 0을 확인하고, 증거의 원래 실행과 최종 배포물
   해시·source·버전·대상 release commit을 확인한다. 실패·누락이면 tag/release/업로드를 하지 않는다.
5. 사용자 지시에 따라 조건 충족 후 `chonamdoo/agents-memory-releases`에 **새 정식 tag `v1.0.0`**과
   최종 검증 asset을 게시한다. GitHub release는 `prerelease=false`, `draft=false`다. 기존 preview
   asset/tag를 덮어쓰거나 GitHub가 SOTA를 보증하는 것처럼 표시하지 않는다. 별도 CI 실행 없이
   로컬 검증을 유지한다. 이 문서나 검사기 생성만으로 배포가 실행되지는 않는다.

## 1. 후보와 평가 입력 고정

실행 전에 Core·SDK 소스/빌드 해시, Python·의존성, Hindsight·E5·BGE 파일,
Jev 모델·판단 정책, 설치기, 마켓 패키지와 배포 번들을 고정한다. 같은 버전 번호라도
바이트가 달라지면 다른 후보이며 변경한 부분에 영향을 받는 증거를 다시 검증한다.
문서만 바뀐 번들은 코드 동일성·변경 범위를 남기고 최종 설치물을 확인한다.

새 독립 평가는 원래 규모인 **196개 입력·40개 이어가기 질문**을 유지한다.
원문·gold·질문·원래 독립 라벨·실제 저자 승인·manifest·harness 해시와
첫 실행 이전 등록 기록이 필요하다. 원래 분류·관련성의 Cohen κ는 각각
**0.60 이상**이어야 한다. 합의 후 라벨의 일치를 독립 라벨 신뢰도로 바꾸지 않는다.
신뢰도 부족이나 누락은 미확인으로 보고한다.

소비된 v22·v27·v43은 실패 진단 자료로 보존한다. 같은 자료를 다시 실행하거나
라벨을 바꾼 결과를 새 독립 통과로 세지 않는다. 원래 질문을 보존하고 질문 수정은
최대 1건 및 원 계약의 실제 두 저자 사전 hash 승인 조건을 따른다.
새 결과를 본 뒤 기준·질문·표본을 선택하지 않는다.

독립 저자의 합성 자료와 실제 사용자 분포의 독립 표본을 구분한다. 같은 주제의
관련 사례를 포함한 합성 cohort의 Wilson 구간을 실제 사용자 전체의 성능 보증으로
일반화하지 않는다.

원문·키·cassette·개인 평가 데이터는 공개 저장소에 넣지 않는다. 공개 기록에는
해시·분모·방법·판정·제약을 남기고, 권한 있는 재검토자가 원본과 대조할 수 있어야 한다.

## 2. 실제 Jev 저장·검색 품질

| 지표 | 고정 통과 기준 | 판정에 쓰는 자료 |
|---|---|---|
| 명시 요청 처리율 | 정확한 전수 비율 1.00 | 각 명시 요청의 저장 결과 또는 이유 있는 거절·감사 기록 |
| 정당한 명시 요청의 실제 저장률 | Wilson 95% 하한 ≥ 0.95 | 정당한 80건; 서버 commit·로컬 applied·Native 문서 확인 |
| 자동 저장 precision | Wilson 95% 하한 ≥ 0.80 | 실제 저장한 자동 후보 중 gold 양성 |
| 자동 저장 recall | Wilson 95% 하한 ≥ 0.60 | 전체 gold 양성 자동 후보 중 실제 저장 |
| 새 세션 이어가기 Hit@5 | Wilson 95% 하한 ≥ 0.75 | 고정 40질문, 기존 출처·답변 충분성 정의의 근거 회수 |
| top-5 잡음 | Wilson 95% 상한 ≤ 0.30 | 실제 반환한 출처 occurrence 중 무관 출처 |
| 압축 생존율 | Wilson 95% 하한 ≥ 0.90 | 실제 compact 완료 후 다음 회상에서 원래 근거 보존 |
| 전체 판단 감사 | 정확한 전수 비율 1.00 | 196건 전체; review와 공급자 전 guard 결과도 포함 |
| 공급자 판단의 raw 감사 | 정확한 전수 비율 1.00 | review를 포함한 모든 공급자 판단 원본 |
| 백그라운드 판단 p95 | Jev ≤ 30초 | 실제 시도의 원래 wall interval 전수, nearest-rank p95 |
| 세션당 판정 요청 | 사용자 턴 + 1 이하 | 실패·중단·인증 실패를 포함한 영속 슬롯 원장 |

Wilson은 양측 95%, `z=1.959963984540054`를 사용하고 반올림 전 값으로 판정한다.
예를 들어 80/80의 하한은 0.954182로 통과하지만 기존 70/80은 0.784972로 실패한다.
40질문에서 최소 36/40은 하한 0.769482로 통과하고, 35/40은 0.738879로 실패한다.
처리·감사의 1.00은 전수검사이며 Wilson 하한 1.00을 요구하지 않는다.

`keep` 응답이나 큐 접수는 실제 저장이 아니다. 누락·실패 입력을 분모에서 빼지 않는다.
검색 잡음의 분모를 반환하지 않은 빈 슬롯으로 늘리지 않는다. 실제 Jev와 고정
Hindsight의 integrated 경로를 측정하며, scripted 판단·replay·검색 전용 합성 자료는
각각 기능·진단 증거로 구분한다.

`recall`의 원래 Hit@5를 `source_search` 결과로 교체하지 않는다. 원문 탐색을
포함한 새 reader 전략은 별도 결과로 보고한다. 필수 근거 **전체** 회수율도 분자·분모를
별도로 보고하되 기존 계약에 없던 숫자 기준을 사후에 만들지 않는다. 생성 답변은
아직 평가하지 않았으므로 답변 정확도 통과나 SOTA를 주장하지 않는다.

## 3. 안전성과 결과 정확성: 위반 0건

다음은 원 계약의 하드 게이트다. 어느 한 항목이라도 위반하면 출시를 차단한다.

- 저장되지 않은 작업의 거짓 성공.
- 명시 요청의 조용한 폐기 또는 감사할 수 없는 거절.
- 인용·도구 출력 속 저장 지시를 사용자 직접 요청으로 승격.
- 같은 ID의 재시도·재시작에서 중복 또는 결과 변경.
- 계정·프로젝트·출처·revision 귀속 오류.
- 비밀값의 공급자 전송 또는 저장.
- 공급자 장애를 discarded/stored로 표시.
- 검색 0건을 전체 기억이 존재하지 않는다고 단정하게 하는 응답.
- 원래 검사기 결함 주입 4종의 미탐지.

권한 철회·팀/개인 경계·정정·삭제도 실제 저장소와 검색 결과에서 확인한다.
단위 테스트 통과와 실제 품질 cohort의 안전성 전수검사를 각각 기록한다.

## 4. 원문 독립 검색과 회귀

`source_search`는 선별 메모에서 제외한 사실을 보존된 제출 원문에서 찾아야 한다.
소유 계정·명시 프로젝트를 순위/제한 전에 적용하고 현재 revision·삭제 경계,
처리 중/review/prompt 제외, 원문 fingerprint·본문 SHA-256을 확인한다.
결과를 미검증 참고 자료로 표시하며 시작 문맥 자동 주입·팀 공유·오프라인 대체를
하지 않는다. 원문 조회 자체의 Jev/Hindsight 호출은 0회여야 한다.

최종 후보의 필수 Core·SDK 회귀는 실패 0건이어야 한다. 필수 설정이 없어서
건너뛴 configured-plugin 검사는 통과로 세지 않는다. OS에 적용되지 않는 검사는
이유·대상 플랫폼·다른 플랫폼에서의 대응 증거를 명시한다.

현재 원문 검색 25개는 실제 shipping cp312/cp313 Core·SDK 설치본 양쪽에서 통과했다.
새 connector의 설치된 SDK·실제 Native 소비 경로도 통과했다. 별도의 완성 설치물에서
production ensure/autostart를 검증하는 기존 검사는 여전히 미실행이다.
실제 로컬 Hindsight의 두 조건 재현 6개도 기능 근거다.
이 실험의 scripted 판단을 실제 Jev 의미 품질 통과로 합산하지 않는다.

## 5. 세 앱·설치·자원

Claude·Codex·OMP 각각 기존 고정 **36건**의 startup/resume/compact·다음 회상
영수증을 확인한다. 각 앱 Wilson 하한 ≥ 0.90을 유지한다. 36/36은 하한 0.903581이다.
앱의 실제 trust·compact 완료와 SDK 훅 실행을 확인하고 도구 목록이나 마켓 설치만으로
자동 수집·자동 회상 완료를 판단하지 않는다. scripted 호스트 API와 실제 공급자
추론의 증거 범위도 구분한다.

현재 후보의 [native 수명주기 기록](../v2.0.0-native-lifecycle/README.ko.md)은
실제 Claude 2.1.319·Codex 0.167.0·OMP 18.18.0 각각 36/36이다. 배포된 CP312
Core·SDK와 실제 native 훅·압축 완료·압축 후 입력을 확인했다. 공급자와 메모리
반환은 loopback 고정 응답이므로 실제 Jev 의미 품질·통합 저장/검색 압축 품질과
첫 대화형 신뢰 승인 근거로 합산하지 않는다. 해당 항목은 부분 완료로 유지한다.

최종 source-free Core cp312/cp313·SDK·SQL schema·설치기의 일치를 검증한다.
실제 설치본의 최초 설치·업데이트·복구/rollback에서 키·모델·DB·연결·미전송 작업이
보존되고, configured release connector가 그 설치본을 소비해야 한다. 지원한다고
표기한 플랫폼/배포 모드의 필수 경로를 검증하거나 지원 범위를 명확히 제한한다.
새 Linux SDK 시험이 과거 Mac 실기기 시험을 자동 갱신하지 않는다.

기존 **2 CPU·4 GiB** 자원 제한과 의존성·고정 모델 조건을 유지한다.
soft RSS 관측만으로 hard limit 준수를 주장하지 않는다. 실제 격리 실행 영수증과
새 latency·원래 호출 원장을 대조한다.

**추가 Jev 197회 승인은 유지**한다. 공급자 전 슬롯을 영속 예약하고 실패·중단도 센다.
자동 재시도나 숨은 warmup으로 예산을 늘리지 않는다. 이 환경에서 추가 호출은 0회다.
과거 `844/1,000`은 snapshot이며 현재 원장 대신 사용하거나 0으로 초기화하지 않는다.
한 번의 cohort도 실패·중단 포함 197회를 넘지 않는다. 예산이 부족해지면 중단한다.

## 6. 이 저장소의 실제 배포 완료

마켓 전달은 공개 `chonamdoo/agents-memory-releases`에서 세 앱의 설치/업데이트를
실행해 설치된 최신 안내·manifest·버전을 확인한다. 공개 main에서 세 앱의
2.0.1 → 2.0.2 업데이트·플러그인 전체 파일 일치와 각각의 미설정 connector
응답 검증을 완료했다. 엔진의 모델 품질과 구분한다. Anthropic/OpenAI 중앙 디렉터리는 별도
등록·심사 트랙이며 GitHub 정식 게시 자체의 필수 조건으로 새로 추가하지 않는다.
중앙 등재를 주장하려면 해당 디렉터리의 실제 공개 주소와 승인 증거가 필요하다.

이 저장소의 **v2.0.0 릴리즈 자산 목록**에 최종 번들·체크섬·검증 기록을 추가하고,
공개 주소에서 다시 받아 동일 해시·설치 동작을 확인한다. 저장소 파일 다운로드와
릴리즈 자산 업로드를 구분한다. 기존 9개 자산은 보존하며 같은 이름의 다른 파일을
덮어쓰거나 기존 tag를 이동하지 않는다. 새 후보 파일명·해시·출처를 명확히 남긴다.

모든 검증과 전달이 끝난 뒤 v2.0.0을 draft=false·prerelease=false로 바꾸고
정식 최신으로 지정한다. 실제 공개 API·페이지·다운로드 readback으로 완료를 확인한다.
401은 배포 전달의 차단 사유이며 모델 품질의 실패/성공 증거가 아니다.
현재 성공한 이전 자산 업로드는 Actions의 별도 토큰 경로였다는 점도 구분한다.
